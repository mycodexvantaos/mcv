# ADR-0001: v0.1.0 Release Recovery Tag

## Status: Proposed

## Context

The original `v0.1.0` git tag and GitHub Release for MyCodeXvantaOS were deleted during a release recovery operation. Subsequent attempts to recreate the exact tag name `v0.1.0` fail with HTTP 422 ("reference update failed").

### Root Cause

The tag name `v0.1.0` is locked by a GitHub internal Release Immutability Record. This record persists even after:

- The release and tag are deleted
- The Release Immutability setting is disabled
- No repository or organization rulesets block the tag
- No tag protection rules exist

### Evidence

| Tag Name      | Result                        |
| ------------- | ----------------------------- |
| `v0.1.0-test` | ✅ Can be created             |
| `v0.1.0.0`    | ✅ Can be created             |
| `v0.1.0`      | ❌ HTTP 422                   |
| `v0.1.0-rc.1` | ✅ Can be created and deleted |

Only the exact name `v0.1.0` is blocked. This confirms the issue is a GitHub internal immutability record, not a configuration problem.

### Attempts Made

1. Direct `git push origin v0.1.0` — HTTP 422
2. GitHub API `POST /repos/{owner}/{repo}/git/refs` — HTTP 422
3. GitHub Actions workflow (`create-v010-tag.yaml`) — HTTP 422
4. Disabling Release Immutability setting — no effect
5. Verifying no repository/organization rulesets — confirmed
6. Verifying no tag protection rules — confirmed
7. Creating test tags (`v0.1.0-test`, `v0.1.0.0`) — successful
8. GitHub Support ticket — pending

## Decision

If GitHub Support cannot clear the immutability record for `v0.1.0`, we will use `v0.1.0.0` as the **recovery publication tag** for product version `0.1.0`.

### Key Distinction

| Field                        | Value      |
| ---------------------------- | ---------- |
| `product_version`            | `0.1.0`    |
| `intended_tag`               | `v0.1.0`   |
| `publication_tag` (fallback) | `v0.1.0.0` |

The product version remains `0.1.0`. The publication tag `v0.1.0.0` is a recovery mechanism, not a version change.

### Why `v0.1.0.0`

1. **Verified creatable**: The tag `v0.1.0.0` has been tested and can be created successfully
2. **Close to original**: The name is clearly associated with v0.1.0
3. **Documentable**: The deviation can be clearly explained in release notes and metadata
4. **SemVer-adjacent**: While not standard three-segment SemVer, four-segment versions are recognized by many package managers and tools

### Alternatives Considered

| Alternative         | Pros                                   | Cons                                                                  | Verdict      |
| ------------------- | -------------------------------------- | --------------------------------------------------------------------- | ------------ |
| `v0.1.0-stable.1`   | SemVer prerelease syntax               | Sorts lower than `v0.1.0` in SemVer; confusing for a "stable" release | Rejected     |
| `v0.1.0+rebuild`    | SemVer build metadata                  | Build metadata is ignored in version precedence; many tools strip it  | Rejected     |
| `v0.1.0-recovery.1` | Clear semantic meaning                 | Still sorts lower than `v0.1.0`; not standard                         | Rejected     |
| `v0.1.0.0`          | Tested and verified; close to original | Not standard three-segment SemVer                                     | **Selected** |
| Wait indefinitely   | Preserves exact tag name               | Blocks all downstream releases indefinitely                           | Rejected     |

## Consequences

### Positive

- Supply chain integrity chain can be restored (tag → release → artifacts)
- Release artifacts can be published and verified
- Downstream users can reference a specific tag
- v0.1.1 security patches can proceed

### Negative

- The publication tag differs from the intended tag
- Some tooling may interpret `v0.1.0.0` as a four-segment version
- Documentation must explicitly explain the recovery tag
- SBOM and provenance metadata must distinguish `product_version` from `publication_tag`

### Mitigation

- Release metadata will include both `product_version` and `publication_tag` fields
- Release notes will explain the recovery tag context
- ADR documents the decision and rationale
- If GitHub Support later clears the `v0.1.0` record, the original tag can be created alongside `v0.1.0.0`

## Release Metadata Format

If the fallback is activated, release metadata will use the following format:

```json
{
  "product_version": "0.1.0",
  "intended_tag": "v0.1.0",
  "publication_tag": "v0.1.0.0",
  "source_commit": "1371a8966c3047bbd95e87308a0bc81e6b72bb41",
  "recovery_reason": "original tag name locked by GitHub internal release immutability record",
  "tag_type": "recovery_publication"
}
```

If GitHub Support successfully clears the record:

```json
{
  "product_version": "0.1.0",
  "publication_tag": "v0.1.0",
  "source_commit": "1371a8966c3047bbd95e87308a0bc81e6b72bb41",
  "tag_type": "standard"
}
```

## Activation Criteria

This ADR moves from "proposed" to "accepted" when:

1. GitHub Support confirms the `v0.1.0` immutability record cannot be cleared, OR
2. The project maintainer decides to proceed with the fallback after the agreed waiting window (24–72 hours)
